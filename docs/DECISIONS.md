# KAD — Решения

> Здесь фиксируются важные продуктовые и технические решения KAD.
>
> Цель документа — помнить не только ЧТО было решено, но и ПОЧЕМУ, какие у решения последствия и когда его следует пересмотреть.

## Правило принятия решений

Перед значимым архитектурным или продуктово-техническим решением оцениваем:

1. Что решение даёт сейчас
2. Какие ограничения создаёт
3. Насколько легко его изменить
4. Что произойдёт при росте проекта
5. Стоит ли небольшая дополнительная работа сейчас более дешёвого изменения в будущем

Текущая потребность не должна автоматически становиться жёстким архитектурным потолком.

## D-001 — GitHub как внешний источник правды

Статус: `DECIDED`

Решение:

GitHub-репозиторий KAD используется как внешний источник правды по проекту.

Чаты ChatGPT являются рабочим пространством, но не единственным местом хранения контекста.

Причины:

- возможность быстро восстановить контекст после перерыва;
- история изменений;
- независимость проекта от одного чата или AI;
- возможность передать проект другому специалисту;
- постепенное освоение нормального Git workflow.

Последствия:

- документацию нужно регулярно поддерживать в актуальном состоянии;
- секреты нельзя хранить в репозитории;
- GitHub не является единственной резервной копией проекта.

Обратимость: `HIGH`

## D-002 — Публичный репозиторий

Статус: `DECIDED`

Решение:

Основной репозиторий KAD является публичным.

Причины:

- KAD строится на open-source экосистеме;
- проект потенциально сможет быть полезен другим;
- публичность стимулирует правильную security hygiene;
- безопасность системы не должна зависеть от скрытности архитектуры.

Последствия:

- любой может видеть опубликованный код и документацию;
- нельзя публиковать секреты и пользовательские данные;
- случайная публикация credential значительно опаснее, чем в приватном репозитории;
- опубликованную информацию нельзя считать отзываемой, даже если позже сделать репозиторий приватным.

Правило:

`Public-first, secret-free.`

Обратимость: `MEDIUM`

## D-003 — Пользователь KAD не равен Telegram ID

Статус: `DECIDED`

Решение:

Telegram является основным интерфейсом KAD, но сущность пользователя KAD не должна быть технически идентична Telegram ID.

Причины:

- возможность резервного доступа без Telegram;
- возможность других интерфейсов в будущем;
- снижение зависимости архитектуры от одной платформы.

Последствия:

- backend должен иметь собственную модель пользователя;
- потребуется механизм связи Telegram-аккаунта с пользователем KAD.

Обратимость: `LOW`

## D-004 — Каждое устройство является отдельным объектом

Статус: `DECIDED`

Решение:

Каждое устройство пользователя хранится отдельно.

Причины:

- индивидуальное отключение;
- отдельные названия;
- статистика;
- лимиты;
- замена устройства без влияния на остальные.

Последствия:

- модель данных немного сложнее;
- управление устройствами значительно гибче.

Обратимость: `LOW`

## D-005 — Mini App не управляет 3x-ui напрямую

Статус: `DECIDED`

Решение:

Цепочка управления:

Mini App → KAD Backend → 3x-ui

Причины:

- безопасность;
- единая бизнес-логика;
- возможность заменить 3x-ui;
- возможность добавить несколько VPN-нод;
- отсутствие инфраструктурных credentials во frontend.

Последствия:

- backend становится важным компонентом системы;
- изменения API между Mini App и backend требуют контроля совместимости.

Обратимость: `LOW`

## D-006 — 30 пользователей не являются техническим потолком

Статус: `DECIDED`

Решение:

Около 30 пользователей — ожидаемая нагрузка ближайшего периода, а не архитектурный лимит.

Причины:

Не создавать дорогостоящие тупики там, где небольшой запас роста можно получить без значительного усложнения.

Последствия:

- не строим инфраструктуру для миллионов пользователей;
- избегаем жёстко зашитых ограничений, которые сложно снять;
- масштабирование учитывается при фундаментальных решениях.

Пересмотреть:

- если число пользователей существенно превысит ожидаемый уровень;
- если появятся несколько VPN-нод;
- если потребуется высокая доступность.

Обратимость: `LOW`

## D-007 — Рабочая документация пока на русском языке

Статус: `DECIDED`

Решение:

Названия файлов, код и технические идентификаторы остаются преимущественно английскими.

Основная внутренняя документация проекта пока ведётся на русском.

Причины:

- документация должна быть прежде всего удобна владельцу проекта;
- снижение порога понимания при возвращении к проекту после перерыва.

Последствия:

- международным участникам будет сложнее читать часть документации;
- при появлении внешнего сообщества важные публичные документы можно перевести.

Обратимость: `HIGH`
